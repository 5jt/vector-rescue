## Introduction

There is a faith and a hope, often expressed in the data processing and lay press, that it will only be a short time before software is written which will let computers be instructed in plain English, and that this will allow end users to interact directly with their machines.

This faith is mistaken and this hope is misplaced. The faith is mistaken because it will be a very long time before computers are able to interpret plain English with anything like the adequacy of a child of five and the hope is misplaced because, even were computers to have the linguistic ability of Dr. Johnson himself, plain English would be an inappropriate language in which to address them – at least for commercial purposes.

What follows is an example of a normal commercial purpose, used to illustrate and justify the above heresy and to put the case for more appropriate, immediately available and cheaper software. It is argued that most software currently used is written in code which is long on bastard English and short on logical and mathematical notation. This is a reflection of the simplistic approach adopted by the first language writers who worked within the constraints of tape and punched cards and minimal storage. Their world was “just one damn thing after another” and most languages have moved ever since with the tottering gait imposed by their bound feet. Hardware is now cheap – the bindings have gone. It is time we learned to leap.

## A taxing problem

Consider the following specification for the calculation of Head Office charges:

> “Head Office Charge is a percentage of a Store’s annual turnover. The percentage varies with the bands into which the turnover falls. For example, the current bands and percentages for Grocery are:
>
> | From | To | % |
> | ---: | ---: | ---: |
> | 0 | 5000 | 5 |
> | 5000 | 8000 | 2.5 |
> | 8000 | 15000 | 1 |
> | 15000 | 30000 | 0.5 |
> | 30000 | - | 0.1 |
>
> ”

There is nothing unusual about this requirement; accountants and analysts are expected to make, or to provide programs to make, such calculations every day of the week. So what is there to say about this specification and the ways it might be met?

Firstly it is ambiguous because it does not make clear which of two common methods of using bands (or ranges) is meant. Think of the boxes that are so favoured for questionnaires:

> **Please Indicate age band:**
>
> | | | |
> | --- | --- | --- |
> | 0-5 | 6-10 | 11-18 |
> | 19-25 | 26-35 | 36-45 |
> | 46-55 | 56-65 | 65+ |

It is quite clear that you must tick only one box. If you are between 26 and 35, then you cannot simultaneously be between 19 and 25.

Next, however painful, think of income tax. Here is the table:

| | |
| --- | ---: |
| 1-16200 | 30% |
| 16201-19200 | 40% |
| 19201-24400 | 45% |
| 24401-32300 | 50% |
| 32301-40200 | 55% |
| 40201+ | 60% |

Suppose your income is £16500; will you pay 40% on all of it? Fortunately not, or no one would willingly earn between £16200 and £18901 (take-home pay at 70% of £16200 equals 60% of £18901). We all know that the real tax calculation is:

> (.3 × 16200) + ((.4 × (16500 – 16200))

i.e. that successive slices of income are charged at different rates. In other words more than one ‘box’ may be ticked.

Head Office Charge, in this case, is meant to be treated like Income Tax – different rates on successive slices of turnover – although, unlike Income Tax, it is regressive (the rate reduces). An accountant would have no difficulty; common sense would tell him to use the second method of calculation.

Programming common sense into computers is another matter entirely and to date common sense languages cannot be bought. So, even if we were able to feed this specification directly into the computer, its action would not be adequately determined.

So how must we write the specification to ensure that it is not misunderstood? How about:

> “H.O.C. is the sum of n(1)% of the first £m(1) of annual turnover, n(2)% of the next £m(2) of annual turnover, . . . and so on. The current values for Grocery turnover are:
>
> | m | n |
> | ---: | ---: |
> | 5000 | 5 |
> | 3000 | 2.5 |
> | 7000 | 1 |
> | 15000 | 0.5 |
> | rest | 0.1 |
>
> ”

Do any of us suppose that this is sufficiently precise for a computer? Probably no one of us is that rash. From which I conclude that if, by some miracle, we had a 4th or 5th generation language which could interpret plain English, we should find the plain (to a computer) English very hard to write and painful to read, because to be precise we should have to write English which is far from plain. The English used in statute law is a good example of what happens when people try to make it precise and unambiguous.

In any case, we cannot wait for miracles; the job requires that we choose some language in which to instruct the computer to make the H.O.C. calculation. What choices do we have? How much code must we write and are the facilities offered by the language sufficient for the job to be cheap to set up and easy to maintain (change)?

While a spread-sheet type of code (Lotus 1-2-3 or Wizard) will look different from a file manipulation type (dBASE II or FOCUS), we can for any of them summarize the job into three steps:

1. find out which band this turnover falls into
2. sum the H.O.C. on all lower bands
3. add the amount due on the remainder.

As it is a small but instructive exercise, I suggest that those among my readers who are familiar with any computer language consider how to code the H.O.C. Of course there is no right way to do it – there are many ways of skinning a cat – but it will be helpful as a particular example of the general charcteristics of code which are discussed below.

## The spreadsheet approach

All computer languages are able to do simple arithmetic. They can add, subtract, multiply, divide, raise to a power and usually extract a square root. Therefore working out a maximum levy on each band of turnover will present no problem and it will follow closely the steps an accountant would take if using a manual spread-sheet. He will tend to use additional columns in the spread-sheet to hold his intermediate workings, thus:

| COL1<br>FROM | COL2<br>TO | COL3<br>% | COL4<br>TO-FROM | COL5<br>CHARGE | COL6 |
| ---: | ---: | ---: | ---: | ---: | :---: |
| 0 | 5000 | 5 | 5000 | 250 | / |
| 5000 | 8000 | 2.5 | 3000 | 75 | / |
| 8000 | 15000 | 1 | 7000 | 20 | |
| 15000 | 30000 | 0.5 | 15000 | - | |
| 30000 | - | 0.1 | - | - | |
| | | | | 345 | |

A program would probably not need COL4. The code for COL5 would be simple:

```
COL5(ROWS 1 THRU 4) = (COL2-COL1) * COL3/100
```

But of course we do not necessarily want all the values in COL5, as that will depend on the turnover which is a variable. The accountant working manually has no problem; each time he re-works he knows what the turnover is and chooses accordingly. Suppose the turnover is 10000. He looks down COL2 and says to himself “is 10000 greater than COL2” and mentally ticks that row if the answer is yes (see COL6). Then the first row of COL6 which has no tick is the one which will hold the calculation for the remainder of the charge:

```
COL5 ROW(COL6 first no tick) = (10000-8000) * 1/100
```

i.e. 20. So the total charge is 250 + 75 + 20 = 345. The accountant has used mental ticks to choose the rows, but what is the program equivalent of a tick?

Some packages may be really clever. They may allow the turnover to be tested against a table of ranges without explicit coding. Then the programmer will provide a remainder calculation something like:

```
COL5 ROW(RANGE=TURNOVER) = (COL2 ROW(RANGE=TURNOVER)-COL1 ROW(RANGE=TURNOVER))
                * COL3 ROW(RANGE=TURNOVER)/100
```

and the sum of the charge rows would be:

```
COL5 ROW6=SUM COL5 ROW(RANGE=1) TO ROW(RANGE=TURNOVER)
```

Less sophisticated software would require a set of tests like:

```
FOR ROWS 1 TO 5
    IF COL2>TURNOVER COL5=(TURNOVER-COL1)*COL3/100 GOTO LABEL
    OTHERWISE COL5=(COL2-COL1)*COL3/100
    NEXT ROW
LABEL COL5 ROW6 = SUM COL5 ROWS 1 THRU 5
```

All programmers will recognize this old friend. It is the loop and can be a lot less friendly than the RANGE type of code especially if it is part of a nest of loops which all too easily turn into a nest of spaghetti.

So why cannot software have more friendly features like the range test? In principle there is no reason why not and most languages allow subroutines to be called from public libraries to perform frequently-needed calculations. In practice the reason is “where do we stop?”. There will be as many friendly features as there are jobs to be done, and the users are bound to want a variation on the theme that no one has thought to provide.

Expert systems are one way to reduce this problem – they acknowledge that the software has been written for a special purpose and build in particular features, ignoring the general cases. This is an admirable solution for areas where the job to be done is well understood and widespread. The two most successful examples are word-processing and conventional spreadsheet accounting.

Suppose however that your job is not run-of-the-mill. What then will be the language of your choice?

## A mathematical approach

The reader will have noticed that the pseudo-code used for illustration contains as many arithmetical symbols as words. Also that the problem centres around the tests (ticks in COL6), which if they are explicit lead to looping code that is difficult to maintain. The code is a clumsy mixture of English or near-English words and a few mathematical symbols, some of which (\* for multiply and / for divide) are not the conventional ones that everybody learnt at school.

Clearly more English does not answer the problem so how about using more mathematics?

Commercial users will respond that they do not need mathematics because “all we do is a bit of simple arithmetic – working out a few percentages – that sort of thing”. This is true if we attend only to *what* the program does and no attention is paid to *how* it does it.

Think of the one bit of mathematics we can probably all remember: *(Ed: the name at least!)* Pythagoras’ Theorem. Somewhere at the beginning of that page in the textbook there will be the phrase “for any right triangle . . .” For any particular triangle, it is easy enough to show by measuring that the square on the hypoteneuse equals the sum of the squares on the other two sides, but Pythagoras said it is true of *any* right triangle and that is an altogether different grandmother (maybe as powerful as a wolf?).

Programs resemble wolves in this respect – they should be able to digest any small girl whatever the colour of her hood. That is, they should provide consistent results whatever the data input, after themselves checking that it is well-formed (that is valid, or girl-shaped). Programs are only written because there are many occasions on which the same algorithm is to be applied to different data. In the commercial world, one-off jobs are done more cheaply by hand or with a calculator; only horrendously difficult calculations would warrant writing a program to be run just once.

There is a word to describe this type of computation – it is said to be ‘generalized’ – and the equivalent mathematical discipline is algebra. In the example above, turnover is a variable, the values in the table are constants, the result is the Head Office Charge and the program is the formula relating them. The difference between the program and ordinary algebra is that a mathematician does not have to describe how to choose the band into which the turnover happens to fall because he is describing the relationship for the benefit of another person and he can assume that the right band will be chosen by “simple inspection”. The programmer must substitute an algebra of “ticks” or “true”/“false” for “simple inspection”. Such an algebra was developed in the last century by George Boole, but its implementation in most languages is crude.

Of course, a programming language will also need to manipulate text. It must allow tests like DIVISION=‘GROCERY’, but much more power than this is desirable. Sorting is an obvious example but there are many others. Given two lists of names, are all items in list A also contained in list B, and if so where? Which elements of A are not in B? Is every element of list A unique? Left/right justify these lists or centre them. Extract subsets and join them . . . and so on.

Assume that we have a language which has a full range of algebraic and Boolean functions and text manipulation. What would the code look like that does the H.O.C. job, and what advantages would it have? Here is an example:

```apl
R←TURN HOC TABLE;BOO;ROW;FROM;TO;PC
⍝ HOW TO USE LOGIC TO AVOID LOOPS
FROM TO PC←↓[1]TABLE
BOO←TURN≥TO ⋄ ROW←1++/BOO
R←+/(BOO×(TO-FROM)×PC÷100),(TURN-FROM[ROW])×PC[ROW]÷100
```

The reduction in quantity of code is small (this has 129 characters as against 136 for the pseudo-code given previously) but look more closely at that code, especially the first line which reads ‘FOR ROWS 1 TO 5’. Suppose the number of turnover bands in the table changes. Then the code must be changed to limit the loop to the number of rows in the table. Now look at the new version. The number of rows is nowhere mentioned. It does not need to be mentioned because the code is generalized – it will work with a table of any size.

Here at last is the answer to the problem which data processing managers have spent years looking for – how to avoid maintenance costs *and* allow users to change the shape of their data.

To see the code at work, we can first look at the contents of the variable and the table of constants:

The action of the code traced was as follows:

line 1:
:   comment only

line 2:
:   split the table into its columns and call them FROM, TO, PC

line 3:
:   create a Boolean variable by comparing the turnover, TURN, with column TO (1500 is greater than 500 & 1200, but less than 2000, 3000 & 999999, so BOO becomes 1 1 0 0 0); the second part of line 3 calculates the number of the remainder row by adding 1 to the sum of the Boolean variable, thus creating the variable ROW.

line 4:
:   uses these intermediate results to sum the remainder (the part after the comma) with the levy on all the rows multiplied by the Boolean which, naturally, reduces those rows corresponding to the Boolean value 0 to zero, while those corresponding to the Boolean value 1 are left unchanged. The Boolean is a mask selecting only those rows where the answer to the question was “yes” – i.e. true or ticked.

## Some serious generalization.

HOC takes a single turnover value and returns the Head Office Charge, but the program of which this is a part will be making the same calculation for many turnover values – perhaps for each department in a store or over successive years for a discounted cash flow. Must we write looping code or can we do all calculations at the same time?

Here is the code to calculate the H.O.C. on any number of turnover values. The code is still 4 lines long, but there is a rather less familiar notation:

¨
:   means ‘each’;

∘.≥
:   means create a table of Boolean values instead of the vector we had before;

⊂
:   means treat what follows as a single object.

```apl
R←TURNS ALLHOCS TABLE;BOO;ROWS;FROM;TO;PC
⍝ HOW TO USE NESTED ARRAYS TO DO MORE AT A TIME
FROM TO PC←↓⍉TABLE
BOO←TURNS∘.≥TO ⋄ ROWS←1++/BOO
R←(+/↑((⊂((TO-FROM)×PC÷100))×¨↓BOO))+(TURNS-FROM[ROWS])×PC[ROWS]÷100
```

## Summary

The purpose of this paper has been twofold. First to persuade the reader that the search for a programming language which can accept plain English will be fruitless. Secondly to demonstrate that the effect of applying a language with the combined power of algebra and logic to a commercial problem is to create concise code which will tolerate major changes in the format of the data offered to it. This has the effect of accommodating change without incurring additional programming costs.

Of course, an intellectual investment must be made in learning the concepts behind the language, but while this will be true whatever software is chosen, there is another factor to be taken into account:

> Mathematics is not likely to go out of fashion

whereas we have all seen VISICALC rise and fall in the space of a few years, and the upstart relational database challenge the hierarchical champion.

Whenever new fields in science and technology are opened up, there is a spate of not very well co-ordinated activity as its potential is explored, but this is followed by a more sober consolidation. The consolidation is almost always mediated by the development of mathematical tools to fit the application of the new technology. For the sort of software considered here, this tool is already available and certainly no more difficult to use than the code it replaces.

As illustration, I attach code taken from the FOCUS User’s Manual. The purpose of the code is to allow FOCUS to call a subroutine which enables it to translate a month number into a month name (1 becomes ‘JANUARY’, 2 ‘FEBRUARY’, etc.). Here is an example of FOCUS code which uses it:

**FOCUS User’s Manual — User written subroutines**

*Example of running MTHNAM*

```
>>DEFINE
>MONTH/I2 = RCOST/1000 ;
>MONTH_NAME/A9 = MTHNAM(MONTH,MONTH_NAME) ;
>END
>>TABLE FILE CAR
>PRINT RCOST MONTH MONTH_NAME
>END
```

The manual supplies a choice of code to do this translation in ASSEMBLER, FORTRAN, PL/1 and COBOL (see Appendices 1 to 4). Here is the equivalent in the language of my choice:

```apl
R←MTHNAME MTH;⎕IO;NUM
⍝ TRANSLATE MONTH NUMBER INTO MONTH NAME
NUM←MTH ⍝ KEEP ORIGINAL NUMBER EVEN IF ERROR
⎕IO←1 ⋄ MTH←(MTH∊⍳12)×MTH ⋄ ⎕IO←0 ⍝  ZERO TO ERRORS

R←(⍕NUM),' ',R

      MTHNAME 1
1 JANUARY
```

## Appendix 1. ASSEMBLER User-written Subroutine MTHNAM (FOCUS User’s Manual)

```
MTHNAM   START  0
         STM    14,12,12(13)          save registers
         BALR   12,0                  load base registers
         USING  *,12

         L      3,0(0,1)              load addr of first arg into R3
```
