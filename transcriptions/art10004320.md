*by Kimmo Kekäläinen*
{ .byline }

I have done it sometimes before in some special cases: provided a menu-driven possibility to change language on the fly from English to Finnish and vice versa. This far, applications have been small autonomous tools with the kind of interface that you normally start building from scratch.

As a Finn, if you even dream of your applications ending up as products and being of interest beyond domestic circles, you must either write them in English from the start, or prepare to support the language of the interface as a user configurable parameter.

How easy it’s going to be to support different languages depends very much on the structure of the application. People like Adrian who went off and developed their own GUI builder tool (Causeway) having text labels, button captions and so on in arrays separated from the code, may find it quite flexible just to provide some kind of GUI to maintain relevant text strings. Whichever the maintaining method is, it has to be something that can be given to someone else (most likely not a programmer) familiar with the language to support.

I started using Dyalog APL in Winter ’92, taking part in the beta test program and since then I have lived on quite happily still carrying along many programming habits that date back those early days. Even today, aside from the general dialogue forms, all the other forms in my applications are created using MAKE\_{MyApp}-like calls, keeping them in a separate layer in the structure of the application. This convention is well supported by WDesign, which is a fine tool, although I have used it quite occasionally. Even when I do use it, I always make final refinements by hand.

What to do with MAKE\_ when you face the need to support different languages?

In this approach all the text strings which appear on the form (except for the items driven directly from data) are hard-encoded in the APL functions. Am I prepared to change programming habits, adopt a different way of defining application structure to get some better language support?

What is the source of your productivity? I know a lot of APLers, Finns and foreigners, many older, a few younger - most having some kind of inclination to ultra-individualism, very anxious to create their own styles, find their own ways to face logistic challenges. In a world as rich as APL spiced up with Dyalog fancy additions to the language like namespaces, there are endless possibilities. Do these discoveries produce a big increase in your productivity? After all, I think it is not so relevant how you do your things - what counts is how consistent you are in your way of doing them.

Well, what to do then with MAKE\_ functions that are part of your adopted structure?

Version 9 of the Dyalog APL interpreter made it possible to manipulate GUI properties directly by simple assignment. This felt good and natural, and despite the fact that it was mainly said to be based on the need to make the syntax closer to the one used in other programming languages, such as Visual Basic, known for their perfect support of third party OLE components, and to prepare for the future .NET development, you were almost tempted to indulge in inadmissible thoughts like "shouldn’t they have implemented it this way from the very beginning? This is APL, after all."

The new supported syntax makes the old

```apl
'MyForm' ⎕ws 'Caption' 'This is mine'
```

be reborn as

```apl
MyForm.Caption←'This is mine'
```

certainly more straightforward and less convoluted thanks to the reduction in the number of quotes needed. Would this be of help in our translatability problem? I started my experiments by creating a little toolset that can be run from the root, or the session namespace or any other namespace. I prefer to run it from namespace **Lng**.

The simple idea is to read all the language-dependent text to appear in a form directly from an active instance and store it in an ASCII file. To test my tool, I took a form written years ago and certainly not with the purpose of trying out such a tool.

To allow the new syntactic constructs, I must make sure that `⎕wx←1` before I load the form.

## MAKE_Tfrm

![The TABLA form, with a caption: “Then I ran following function to store all relevant text properties in created form: '#.Tfrm' Lng.LanguageFile_create 'c:\Tabla\Lng\Tfrm.fin' and took created file into Notepad and started translations and finally saved it along target language to file named 'c:\tabla\Lng\Tfrm.eng' and ran Lng.LanguageFile_load 'c:\Tabla\Lng\Tfrm.eng'. You see:”; below, the form’s File menu in English (Open table file, Project definitions, Asci-preview, Conversions - table files, Packing a file …) beside the Tfrm.eng file in Notepad, with lines such as #.Tfrm.Caption=Table Analysis TABLA ver 1.2 and file.open.Caption=&Open table file](art10004320/tabla.jpg)

The principle on which the tool is based is that the text file with all the strings can be given to your expert in the target language. The form instance is still created with the MAKE\_ function and all the GUI strings are substituted at runtime with the ones read from the ASCII file after the form is created. With the speed of execution of today’s workstations, nobody notices any speed delays.

The default language to be used is a system parameter and so are all the supported languages. They can be read from an Appl.ini file or from the Windows registry at application start-up.

The language to be used is stored somewhere safe as a global variable or DATA property: my choice is to use

```apl
⎕SE.∆_lang←'fin' ⍝ or 'eng' or 'swe'...
```

The naming conventions then are quite consistent and clear. Let’s say the application root directory is **C:\Tabla**. Then the place for the text source files would generally always be **.\Lng**. If you want it to run independently of the working directory, you must use the full path. I also associate the file extensions to the language identifier. The function that associates the file name with a particular combination of form and language is *Form_texts* (see functions).

So, to update all the captions, labels and other texts after creating the form, just execute:

```apl
MAKE_Tfrm ⋄ Lng.LanguageFile_load Form_texts 'Tfrm'
```

Yes, I am aware that there is a world of things to consider beside MAKE\_ when you seriously aim for a language-independent solution. Still, for me this looks like a promising start and saves me from the need to re-invent everything at the same time. At least this is of great help in solving the problem associated with the strings hard-encoded in the source code, which I consider the trickiest aspect of the general problem. Anyway, I think the best benefit comes from the fact that you don’t have to touch existing MAKE\_-code at all. To get the effects, just add a line after each MAKE\_ call, and magically the form appears fully translated.

Captions and contents for general modal dialog forms like OK-, WARN- and similar messages which indeed are a relevant part of any application, are most likely to be stored into some tables organised by language version with identifying hooks and read from external files, supposed to be easily editable.. Help files are in general already separate from application code and can be translated using the tools they were created with in the first place.

I include the code I use. Make sure to check the comments in the code for the rules concerning running the functions under different namespace conditions. I expect it to be flexible enough to handle most obvious situations. If you are interested in trying this yourself and want to avoid to have to retype all the code, just contact me and ask for a working workspace.
