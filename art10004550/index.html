Exploring ActiveX Data Objects

from Dyalog APL

by J. Korablev and G. Roche (Gunter.Roche@gmx.de)

Abstract This paper presents a short overview of the ActiveX Data Objects (ADO) model and the main steps for application development in Dyalog APL. ADO was created by Microsoft in order to provide an easy-to-use application level interface to currently known data sources. This interface is based on the underlying system service OLE DB and is used in tools for rapid application development. ADO is easily accessible for users, because it is included with popular Microsoft products such as Internet Explorer 4.0, Internet Information Server 4.0 etc. ADO is also available for download from the Microsoft Web site (the SDK, the Microsoft Data Access Components 2.0, and the Data Access SDK). The implementation of ADO in Dyalog APL is based upon OLE Automation, a mechanism that allows one application to control another, and which provides the ability to mix code written in different programming languages.

Introduction. OLE DB and ADO are the low and high levels of interface that enable Universal Data Access. This is Microsoft strategy for providing access to all types of information from a variety of data sources (relational and non-relational data, mainframe ISAM/VSAM, hierarchical databases, emails and file system, text, graphical, and more). For each kind of the data source there is a specific service component, called a provider. An integral part of OLE DB is the OLE DB Provider for ODBC, which enables OLE DB to communicate with today’s popular ODBC drivers and data sources.

There is a definite difference between ADO and OLE DB from the developers’ point of view, OLE DB enables universal access to any data. ADO facilitates it for developers of programs. Since ADO is located on top of OLE DB, it has a low memory overhead, and a small disk footprint. ADO supports key features for building client/server and Web-based applications, including the following:

* Independently-created objects. This allows the programmer to create and work only with the objects that are required.

Note that OLE is very dependent on the Visual Basic programming language and APL syntax is more restricted than Visual Basic. This discussion ADO object model aims to cover the main steps involved in application development with Dyalog APL.

The Connection (drives a connection under a definite provider), Command (executes a command, such as a command text, stored procedure, command prepare etc.), and Recordset (a set of records returned by commands) objects are top-level objects that can be created and destroyed independently. They are

registered in the Windows registry as ADODB.Connection, ADODB.Command, and ADODB.Recordset, respectively.

In addition to these three top-level objects, there are four other subsidiary objects, that exist only within the context of their parent objects, and cannot be created separately, namely Parameter, Field, Error and Property.

The Parameter (ADODB.Parameter in the Windows registry) object can be created. independently of a Command object. In this case it must be included in a Parameters collection Command before it is used command. Parameter objects can be created from the Parameters collection too, where they are placed automatically result statement syntax setting Command object. Calling its Execute method assigns corresponding Value properties to all Parameter objects in the collection. It provides the facility to use bind variables in SQL expressions. The Field object provides structural information about a single column of data within a Recordset. The Error object supplies extended error information about an error condition generated by the provider. The Property object describes provider-defined characteristics of an ADO object.

Each of the Error, Property, Parameter and Field objects are accumulated in the corresponding collections: Errors, Properties, Parameters, and Fields. (A Collection is a special kind of object that contains a set of other objects; you can think of it as a vector of objects.)

There are two ways to access the properties and methods of ADO objects from Dyalog APL. If, when an instance of an ADO object is created as an OLEClient object, the AutoBrowse  property is set to 1 (the default), the methods and the this object appear as functions and variables in the OLEClient namespace. In principle, with a few exceptions, a method corresponds to an APL function and a property corresponds to an APL variable. This is possible because ADO objects have a type-library file with type information, that includes the name of the methods and properties exported by the object, together with descriptions of the arguments to each method and descriptions of the of each property. An alternative, is to specify AutoBrowse as 0 when creating the OLEClient. This causes Dyalog APL to create an empty namespace whose methods are accessible using 3 UNQ and whose properties may be queried and set using This approach is faster, because APL does not have to read the object’s type-library for the information it needs to establish functions and variables corresponding to the object’s methods and properties. However, in practice it is much better/safer/more maintainable to leave AutoBrowse as 1.

Basic ADO Application Steps This section describes the general flow and the for developing ADO applications in Dyalog APL. Most such applications use some variation of the following steps:

* Connect to a data source by means of a Connection object. Optionally, begin an explicit or implicit transaction.

* Optionally, create a Command object to represent an SQL command with or without parameters.

* Optionally, if a parameterized command is involved, specify columns, tables, and values in the SQL command as variable parameters via the Parameter object.

« Execute the command. This can be carried out by the Command, Connection, or Recordset object.

* After executing, a result is returned in a storage object Recordset.

* Optionally, view, sort, filter, and navigate the data in a Recordset.

* Edit, add, delete the data in a Recordset. Work directly with columns or rows Fields collection and Field objects.

* Ifitis all right, update the data source with changes from the object Recordset.

* Ifa transaction was used, commit the changes made during the transaction. This is a function of the Connection object.

* Retrieve the providers’ information about each object via a Properties collection. Each collection contains a set of Property objects specific instance of an object.

* Retrieve the information about errors during connection (Error objects via Errors collection).

Control the Transactions

When a set of changes that were made to the data source must be saved or cancelled as a single unit, the following transaction methods of the Connection object are employed:

* BeginTrans begins a new transaction;

* CommitTrans saves any changes and ends the current transaction;

* RollbackTrans cancels any changes made during the current transaction and ends the transaction.

In the above code #.C1.BeginTrans included, for example, after #.R1.MoveFirst and #.C1.Commitfrans or #.C1.RollbackTrans after #.Ri.Update @.

If a provider supports it, the transaction can also be controlled using the Execute method of the Connection object or Command object, with command text for the begin, commit and rollback transaction (for example, BEGIN TRAN', COMMIT TRAN!, ROLLBACK TRAN" of TransactSQL of MS SQL Server).

Not all providers support transactions. The sign that the provider supports transactions is the provider-defined property Transaction DDL’, appearing in the Connection object’s Properties collection. If the provider does not support transactions, calling one of these methods will return an error.

Any operation on the database involving ADO objects can generate one or more data provider warnings and errors. As each error or warning occurs, one or more Error objects are placed in the Errors collection of the Connection object.

An Error object’s properties can be retrieved in order to obtain specific details about each error or warning, including the following:

* The Description property, which describes the situation in detail.

* The Number property, which contains unique identification of an error or a warning.

* The Source property, which identifies the origin of a problem.

* The SQLState is a five-character code for any problem encountered during the Processing of an SQL statement.

* NativeError properties, which describe the provider-specific error or warning code.

Comparison between Different Approaches to Data Access

Dyalog APL can choose from many of Microsoft's technologies for accessing data sources, These include:

* Open Database Connectivity (ODBC) for relational data via the ODBC API code,

124

VECTOR Vol.16 No.4

* Remote Data Objects (RDO) for ODBC data.

* Data Access Objects (DAC) for local data (Microsoft Jet database engine).

« DAO for ODBC data (ODBCDirect).

* Microsoft ActiveX Data Objects (ADO) for all types of data.

All the above-mentioned object models (RDO, DAO, ODBCDirect, ADO) were invented to give developers the ability to avoid direct programming of the corresponding API. They are an artificial layer over this API, and provide all their functionality in an object model of type easy-to-use , rather than in a collection of function calls ina DLL.

Today, there are features that are not available in ADO, but which are present in one of the alternative object technologies. However, the aim of ADO is to become a superset of DAO and RDO.

One of ADO’s benefits here is the declaration of a simple and understandable language for accessing data. ADO now plays the role of the standard data access language for Microsoft tools and program products. For example, the current versions of Internet Information Server, Internet Explorer, Visual Basic, Visual C++, and Visual J++ ADO as their primary data access and control language. The next release of Microsoft Office promises to do this too.

The use of ADO from Dyalog APL compared with the base ODBC API DLL shows on the one hand a little more general performance of the DLL-approach, because of the usual benefit of compiled DLLs vs. interpreted Dyalog APL. On the other hand, the performance of the base function calls in the DLL compared to the speed of the methods in ADO for connecting, query preparing, executing, fetching and closing is practically equal. Finally, ADO is more universal than the DLLs in offering functions, data types, and data sources. Additionally, ADO provides full control of all steps for data access in Dyalog APL. The

small differences in performance can be mitigated by optimal organisation of the program structure .

Conclusions ADO provides the capability to carry out query and manipulation (SELECT, INSERT, UPDATE, and DELETE statements) of all types of data. To access most popular telational data ADO can use OLE DB directly, or it can use the OLE DB Provider for ODBC. To access other types of data, there are other kinds of data providers.

Not all ADO features were discussed here, for example:

« Free threading, that allows one to build very powerful and scalable Web server applications.

* Asynchronous queries, that return control to the application before the query is completed.

° Remote Recordsets, that allow one to retrieve and manipulate data remotely, then update the source.

* Events, that allow ADO 2.0 to expose a list of events that used to control all aspects of the connection, query, and table access process.

Since ADO is a COM-based component, called using the Automation interface, Dyalog APL can use ADO and combine high-performance access to any data source with its own capabilities of efficient array data processing.
