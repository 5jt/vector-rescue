Transcribed from the printed issue; not yet reviewed. Read it in the PDF of the issue, page 48

by Jonathan Barman

Introduction¶

There has been a tremendous amount of hype about XML being the "the ASCII of the future". Initially I was suspicious as all seemed rather pointless. Having seen how and where XML is used the penny has finally dropped. Clearly separating the data, using XML, from the display, using HTML, seems to be a very sensible idea. Another of the ways in which XML is used is to transfer of data between completely independent programs and machines. The transfer is normally on the Web but can be between any machines networked together. Having a clear, self-documenting, medium when one is trying to write a program to pick up data from another source if obviously a great help. I was interested in the Web site www.xmlrpc.com which contains a specification for using XML for remote procedure calls and which appears to be implemented on several platforms.

This article is about the way in which XML can be manipulated using Dyalog APL version 9 with the new-style object syntax.

XML Basics¶

XML is a simple way of structuring data. It looks very like HTML but the tag names are whatever you need to define the data. The general idea is to make it self documenting. Tag names should describe the data so that anyone looking at the XML can easily see what is going on.

XML is fussier than HTML in that all tags must be closed and the nesting must be correct. If you are familiar with HTML then XML is easy to create. For example, an APL array could be defined as follows:

<array>
  <rank>
    <dimension>2</dimension>
    <dimension>3</dimension>
  </rank>
  <data>
    <number length="3">0 1 2</number>
    <array>
      <rank>
        <dimension>2</dimension>
      </rank>
      <data>
        <char length="2">AB</char>
      </data>
    </array>
    <number length="2">4 5</number>
  </data>
</array>

The <array> element has two elements <rank> and <data>. The <rank> element contains <dimension> elements which specify the shape of the array. The <data> element contains elements which specify the data type of the value. A data type can be <number>, <char> or an <array> for a nested array. The <number> and <char> elements have an attribute length specifying the length of the data each contains.

Whilst this simple scheme shows how easy it is to define data structures in XML it is not adequate to fully describe an APL array. For example, the character data element may need to cater for any character out of ⎕AV. Also it might be necessary to precisely define empty arrays with full prototype information.

If you have never seen XML before the tutorial site www.xml101.com contains some good examples and clear explanations.

XML Document Object Model¶

Microsoft distribute an XML parser with Windows, MSXML.DLL. This has been upgraded for Windows 2000 to version 2.6 which is in MSXML2.DLL If you have installed .NET there is yet a further upgrade to MSXML3.DLL. I have used MSXML version 2.6 for all the examples because I am running under Windows 2000 but, hopefully, I have not used any of the new features.

The base object of the parser is the Document Object Model (DOM). The main thing that this contains is the Root Element of the XML. The Root Element contains collections of Nodes. A Node within the collection may be one of several types which include Attributes and Elements.

Dyalog APL and MSXML¶

The latest version of Dyalog APL, 9.0, includes a major improvement in the way COM objects such as MSXML can be accessed. In order to show off the power of the new version code will be developed in both 8.2 and 9.0 so that a direct comparison can be made between the two version.

Both versions access the basic DOM object in the same way:

      'xDOM'⎕WC 'OLEClient' 'MSXML2.DOMDocument.2.6'

The above is only valid if you are running under Windows 2000. Otherwise the second argument would be 'MSXML.DOMDocument'. I find that it is always best to check the exact spelling by looking at the array produced by

      a←⊃¨'.'⎕WG'OLEServers'

There are two methods for loading XML into the DOM; load which loads from a file and loadXML which loads a character vector. Again, both 9.0 and 8.2 have the same syntax:

      xDOM.load 'Example1.xml'
1

The 1 returned indicates that the XML has loaded without error. If an error occurs then the error information is held in the parseError property. In this case versions 9.0 and 8.2 are different:

In Dyalog 9.0 you can assign objects to variables, so you don’t have to use ⎕WC. This facility is fully extended throughout the language so that :with arguments can also be an object rather than a character vector giving a namespace path. It also allows the dot syntax that is standard in other programming languages, so it is possible to access the reason for the error with xDOM.parseError.reason.

The Load function, defined on line [4] and called on line [28], is much the same as defined above but I wanted a zero return code to indicate success. It checks that the XML has loaded correctly and also checks that the root node has the correct name. Line [6] shows off the way in which the new namespace syntax can now include arbitrarily complex statements enclosed in parentheses between the dots.

The DOM object actually contains a collection of child nodes, which will be explained later on. The documentElement property (referenced on line [7] and [29]) contains the root node. There can only be one of these otherwise the XML would not have loaded correctly. Array is therefore called with the root object as its right argument.

The Shape function, called on line [10] and defined on line [14], uses the selectNodes method on line [15] to get the dimension nodes. where the argument 'rank/dimension' is an XPath expression which specifies the path to the required nodes. If something goes wrong then the method returns NULL so the variable dm is tested to see if it contains a scalar zero. dm is not an array, it is a Selection Object containing the nodes found. Line [16] checks the length property to see if there are any dimensions and then line [17] uses yet more complex expressions to convert the text property of each node into numbers. Before the Editor pointed out this new feature I was much mystified why statements such as xRoot.childNodes.(item i).nodeName gave a VALUE ERROR. I correctly guessed that the variable i was being masked on the way down the object hierarchy, but did not realise that this was deliberate or how useful it could be.

Back to the Array function on line [11] the nodes containing data are selected with a set of paths separated by an OR (|) symbol. The XPath documentation in MSDN is listed under XSLT which I did not find until I had virtually finished this article; it is well worth careful study if you are going to manipulate XML. Line [13] is thanks to John Scholes where the reduction operator is used to place the Value function between each pair of nodes to catenate all the results together. Because reduction operates from right to left, but we want to work from left to right, the indices are reversed.

The Value function is therefore dyadic taking a node as its left argument and the data to be catenated as its right argument. The Length function selects the length attribute by putting an AT (@) sign in front of the name. Lines [20] to [22] convert the data and catenate it to the right argument. Line [23] is not really necessary as the function can only be called with nodes of the correct names.

Processing Instruction and Document Type Definition (DTD)¶

In order to keep things simple I have left out the Processing Instruction and DTD in the example XML above. Ideally this should have had the following inserted before the first <array> tag:

<?xml version="1.0" ?>

<!DOCTYPE array [
<!ELEMENT array (rank?, data?)>
<!ELEMENT rank (dimension*)>
<!ELEMENT dimension (#PCDATA)>
<!ELEMENT data (number|char|array)*>
<!ELEMENT number (#PCDATA)>
<!ELEMENT char (#PCDATA)>
<!ATTLIST number length CDATA "1">
<!ATTLIST char length CDATA "1">
<!ATTLIST char xml:space (default|preserve) "preserve">
]>

The first line is the Processing Instruction which merely states that this section is XML version 1.0. The remaining lines are the DTD. These two items appear as children of the DOM object, so that is why the documentElement property was accessed in the above code to get at the root node, rather than looping through all the child nodes.

The name given as the argument to !DOCTYPE must be the name of the root node. Tag names in XML are case sensitive so given this DTD it is not necessary to ensure all the names are in the correct case.

The expression <!ELEMENT array (rank?, data?)> states that an <array> element can only contain <rank> and <data> child elements, in that sequence and no other data. The ? following the names means that there may be zero or one occurrences of each.

A child entity name may be followed by nothing, which means that it must occur exactly once, a query (?) if it is to occur zero or once only, a plus (+) if there must be one or more occurrences, or a star (*) if it can occur zero or more times. Putting the decoration after the enclosing parentheses means that it applies to all of them.

The declaration dimension (#PCDATA) means that there may be data between the start and end dimension tags.

Specifying child entities separated with vertical bars (|) means that any may occur in any sequence. The data element has been defined in this way.

Attributes are defined with !ATTLIST element-name attribute-name attribute-type default-value. The attribute types and attribute defaults may be as follows:

Attribute Type Meaning
CDATA Character data
(value|value|..) One of the given values must be included
ID An unique Id
IDREF The Id of another element
IDREFS A list of other Ids
NMTOKEN A valid XML name
NMTOKENS A list of valid XML names
ENTITY An entity
ENTITIES A list of entities
NOTATION A name of a notation
Xml: Predefined
Attribute Default Meaning
#DEFAULT value If the attribute is not present then the value is assumed
#REQUIRED An attribute value must be included
#IMPLIED The attribute is optional, but no default is available
#FIXED value The attribute always has the same value regardless of the value specified in the XML

The example DTD has defined the default attribute values in double quotes rather than using #DEFAULT. For example, the number attribute could have been defined as !ATTLIST number length CDATA #DEFAULT 1.

It is a good idea to include a DTD because otherwise you have to carry out much more checking in the code. For example, without a DTD it is permissible to include data between the array tags.

      xDOM.loadXML'<array>data</array>'
1

But, with a DTD the parser recognises that this is not permitted.

      xDOM.loadXML dtd,'<array>data</array>'
0
      xDOM.parseError.reason
Text is not allowed in this context according to DTD/Schema.

Expecting: rank, data.

Another useful facility is to control white space. The XML parser normally removes white space which means you don’t actually get what is in the XML. Defining character arrays can be quite difficult if spaces are removed in some arbitrary way. The xml:space attribute ensures that spaces are preserved for character data, but this can be overridden if you really don’t need it. The following shows the effect on spaces.

      x←'<array><rank><dimension>20</dimension></rank>'
      x,←'<data><char length="20">     A      B    </char>'
      x,←'</data></array>'
      ⎕SE.DISPLAY 2⊃XMLToArray x
.→-------------------.
|A      B            |
'--------------------'
      ⎕se.DISPLAY 2⊃XMLToArray dtd,x
.→-------------------.
|     A      B       |
'--------------------'

Another way of dealing with spaces is to use the CDATA definition which can be used anywhere PCDATA is expected.

      x←'<array><rank><dimension>20</dimension></rank><data>'
      x,←'<char length="20"><![CDATA[     A <>   B    ]]>'
      x,←'</char></data></array>'
      ⎕SE.DISPLAY 2⊃XMLToArray x
.→-------------------.
|     A <>   B       |
'--------------------'

The object hierarchy tends to force one into loops which can be difficult to replace with APL arrays. As far as I can see the main advantage in using MSXML is where existing XML needs to be edited and then saved. MSXML is full of useful methods such as replaceChild, removeChild, insertBefore etc. etc.

Creating XML using MSXML¶

If you need to use MSXML then the following functions show how to set about the task. Also, there are several characters in ⎕AV which seem to give MSXML a bit of a headache when reading XML so it is interesting to see what MSXML does when generating the XML.

The easiest way to start is to load a bit of XML into an empty DOM object, in fact this appears to be the only way to define a DTD.

      'xDOM'⎕WC'OLEClient' 'MSXML2.DOMDocument.2.6'

I don’t want ArrayToXMLms itself be a direct definition function because on line [42] there is a call to ⎕WC which in direct definition mode results in a global variable being created. If there happened to be a variable x lying around in the Workspace then the call to ⎕WC would result in a DOMAIN ERROR. Also, you would have to remember to )ERASE x when the function finished.

The calls to the appendChild method (line [6] is the first) return the address of the child node, which has been updated to include a reference to its parent. The documentation states that if something goes wrong a NULL is returned rather than an address. Ideally one should check the result to see if the operation has been successful. Setting attribute values seems too easy, as line [29] demonstrates. The results are not particularly pleasing as the XML is not formatted into lines, but it all seems to work correctly. It is interesting to see how MSXML copes with the full ⎕AV and exactly which characters it finds difficult.

Creating XML using MSXML in Dyalog version 8.2¶

I have not attempted to create the equivalent function using MSXML in Dyalog 8.2 because the character version is perfectly adequate and version 8.2 is quite tricky. Direct definition would not be applicable, but otherwise the general scheme would be much the same as the 9.0 version. Conclusion¶

XML seems to be quite simple to manipulate with MSXML and Dyalog APL. Version 9.0 is a great improvement over 8.2, but while more tedious, 8.2 is perfectly capable of carrying out the task.
