Stack Operations

by Phil Chastney (phil@amadeus-info.freeserve.co.uk)

1. Introduction 1.1 APL uses infix notation. This has the advantage of being familiar; it has the disadvantage of being ambiguous in anything other than the simplest of expressions.

Prefix and postfix notations are unambiguous. This was proved some time ago by Lukasiewicz, but since nobody in Western Europe can pronounce his name, postfix notation is known simply as Polish notation, and prefix notation is known as Reverse Polish”. Forth and Postscript are perhaps the best known examples of such notations, although they used by some scientific calculators.

Ambiguities can be avoided with infix notation, either by fully parenthesising each expression, or by the use of some form of dot notation’, though neither has been widely adopted.

1.2 Notwithstanding the ambiguity, infix notation has been the rule rather than the exception. A number of methods of overcoming the ambiguity use: left- to-right order of evaluation, right-to-left order of evaluation, and operator hierarchy. Most languages use two or three of these methods. Given a hierarchy, there will situations where non-commutative operations occur at the same level, a simple example being 3*#3**3 (where the double asterisks denote exponentiation). Just what does that expression evaluate to? Some languages would evaluate it left-to-right (to give 19683) and some would evaluate it right-to- left (to give the rather different 7.62e12),

It is common practice in compilers to translate infix expressions to postfix, using a stack and Dijkstra’s shunting algorithm. This makes for easier code generation and faster execution.

1.3 This could be done with APL. Not in the general case - because monadic vs. dyadic use cannot be distinguished until we know all the side-effects of execution up to that point, but in most cases - because the standard recommends (but does not require) that the syntactic class of tokens is bound when execution of a line commences. But why bother with translating to postfix? APL syntax is so brilliantly designed that it is possible to interpret a statement without needing

During interpretation, the occurrence of a right bracket in the input stream can signify either the start of an axis definition, or the start of an index list. This is not a problem: the distinction can be made during the left-to-right tokenising phase.

If we ignore its use in defining the axis operator, the occurrence of a right bracket in the input stream tells us two things:

Part of the answer is that the stack is not visible to the programmer. Or maybe it is visible, but it is not directly accessible. Which leads into another interesting question: what would life be like if the stack were fully accessible?

This is not such a far-fetched notion: POP-2, for instance, made the stack available, along with facilities to assign a value to the stack, and assign a value from the stack ~ push and pop, essentially. Apart from the obvious assembler-like uses, this mechanism used to construct a partial-binding mechanism, where k arguments of an n-place function are bound, to give a new (1-k)-place function. 5.2 Parentheses represent a minor break normal flow of control; a function call represents a major break in the normal flow of control. Both use the stack to achieve the desired effect. That is to say, when we apply a function, the application operator, which applies a function to its arguments, is a stack operation.

The major steps in applying a function are: * preserve the calling environment, including a return address and an image of the current state of the symbol table;

* close the function, i.e., bind the arguments in appropriate fashion - name, value, pointer, whatever;

* transfer control.

5.3 One of the differences between C and Pascal is the order of evaluation of arguments - interfacing the two requires a bit of jiggery-pokery in assembler, to manipulate the stack.

Order of evaluation is not a problem in APL: we evaluate the right argument, derive the function (if necessary), check whether a left arg is permitted, check whether a left arg is supplied, if so we evaluate that as well, and then apply the function to its argument(s).

A function applied to a list can look like an n-place function, but the order of evaluation specifies that we build the list from the right, then apply the function. There is no ambiguity.

5.4 Imagine if it were possible to preserve environments: backtrack programming would be so much simpler. At the moment, it is necessary to identify the values which characterise a partial solution, and administer your own stack. With environments as first class objects, it would be possible to run process A until it failed to improve by the required amount, then suspend it, revert to the calling environment, and start over with process B. If process B failed to with the goods, then we could re-activate process A. Languages exist which permit this sort of swapping, through the use of reserved words, but they appear to be largely experimental: other languages offer similar facilities via threads and/or autonomous processes, but it is rarely obvious when the result is intended to be backtrack programming,
