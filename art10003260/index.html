Missembling

Vector 5:2, page 105

system interfaces programming techniques humour

Transcribed from the printed issue; not yet reviewed. Read it in the PDF of the issue, page 105

by Allan Gay

The discerning reader will have noticed a couple of howling errors in my previous “Dissembling” article which I feel obliged to correct.

The first was, of course, the absolutely unforgiveable misspelling “wanged”, which should, as all lovers of the English language appreciate, have been “whanged”. My sincere apologies go to all those who were shocked into catatonia by this affront to their sensibilities – if they can still hear me.

The other error was a trivium which merely rendered the Assembler code completely unusable. I refer, of course, to the first Divide instruction which, operating on 52 significant bits (after shifting), produced a quotient requiring more than 31 bits for its expression and so yielded a fixed-point divide exception.

It’s interesting to note that APL, which holds large values in exponential format and migrates freely between formats as the data varies, is unaffected by such narrow limitations. Because I neglected to take this fact into account, the error was not revealed by the simulation which was the subject of the article.

It’s also interesting to note that the fixed point divide exception is the classic trap which lies in wait for the unwary writer of a TOD-clock decoding routine – and I fell headlong into it.

….

Examining the smouldering remains of the program, I confirmed that the first Divide instruction was the critical one. Subsequent divisions would produce results of manageable size once I was over that first hurdle. The question was: how to perform the division?

Eleven year old readers who have passed their mathematics exams will see the answer immediately. Those who, like me, re-sat the same exam at the age of thirty-five – and failed – may find the following description of interest. If not, they can always sneak off to the pub during the heavy bits.

The trick of it is to split the number into two manageable parts, divide them separately, note their quotients and remainders, and then combine them. Since we are working with 32-bit registers, of which the high order bit is reserved for a sign, it seems reasonable to split off the low-order 31 bits.

One snag which we have to watch out for is that the high-order fragment’s remainder and quotient after division are 2*31 times greater than they seem. Consequently, they must be multiplied by shifting, after which the remainder must be divided again. This gives us three quotients and two remainders for respective summing.

The other snag is that, when we sum the two remainders, we may get a result which exceeds the divisor. In this case, we must subtract the divisor from it and increment the sum of the quotients by 1. Since we are summing only two remainders, our result cannot but be smaller than twice the divisor, so a single incrementation is all we’ll ever need.

The following APL function demonstrates the principles involved.

     ∇ R←DIV ALGORITHM TOD
[1]   ⍝
[2]   ⍝ Assume TOD contains the 52-bit clock value
[3]   ⍝  (ie. the value after shifting) and
[4]   ⍝  DIV contains our chosen divisor.
[5]   ⍝
[6]    HI←⌊TOD÷2*31 ⍝                  Get high-order half in HI.
[7]    LO←(2*31)|TOD ⍝                 Get low-order half in LO.
[8]   ⍝
[9]    HIQUOT←(2*31)×⌊HI÷DIV ⍝         Divide HI.  The multiplication
[10]   HIREM←(2*31)×DIV|HI ⍝           by 2*31 reinstates significance.
[11]  ⍝
[12]   HIQUOT2←⌊HIREM÷DIV ⍝            Divide remainder, giving more
[13]   HIREM←DIV|HIREM ⍝               quotient and proper remainder.
[14]  ⍝
[15]   LOQUOT←⌊LO÷DIV ⍝                Divide LO, giving more quotient
[16]   LOREM←DIV|LO ⍝                  and more remainder.
[17]  ⍝
[18]   QUOT←HIQUOT+HIQUOT2+LOQUOT ⍝    Sum all three quotients.
[19]   REM←HIREM+LOREM ⍝               Sum both remainders.
[20]  ⍝
[21]   →(DIV>REM)/END ⍝                If sum of remainders exceeds
[22]   REM←REM-DIV ⍝                   divisor, subtract divisor from
[23]   QUOT←QUOT+1 ⍝                   it and increment quotients' sum.
[24]  ⍝
[25]  END:R←QUOT,REM
     ∇

Now that the principle has been demonstrated, it’s time to put it to work. The following Assembler code does so. Afterwards, we can look at its simulation in APL.

The code given below replaces just four instructions in the previous article’s example. The original instructions (with their comments) were:

         LM    6,7,0(3)         . R6-R7 CONTAIN INPUT DWORD DATE.

*-------SPLIT SECONDS OFF------

         LR    2,6              . PUT MICROSECS FRACTION ASIDE IN R2.

         SR    6,6

The replacement instructions are, ahem, a little more extensive:

         LM    2,3,0(3)         . R2-R3 CONTAIN INPUT DWORD DATE.

The AL and ALR instructions may require a word of explanation. The usual System/370 fixed point binary Add instructions operate on signed values. The high order bit of a 32-bit register is used to carry a sign: an off-bit denotes a positive value and an on-bit denotes a negative value.

AL (Add Logical) instructions view all 32 bits as data and set the condition code to indicate whether a carry-out occurred. When, as here, we operate on a value which straddles two adjacent registers, we can use the AL and ALR instructions to add values into the low-order register of the pair and, if a carry-out occurs, detect it and increment the high-order register.

General services used by the simulated instructions:

ADDR checks/converts an integer to a 24-bit Boolean

BIN2HEX converts a Boolean to hexadecimal representation

FULLWORD checks/converts a decimal integer to a 32-bit Boolean

TRACE displays regs, condcode and current instruction image

Listings of all these functions follow. Assembler buffs will confirm that the foregoing represents only a small fraction of the System/370 repertoire. These are easy ones to simulate because they all do things with registers. I have yet to devise a way of simulating mainstorage accesses, although of course it is easy enough to supply literal values directly, as the simulation indeed does.

Not wishing to get caught again by fixed point overflow situations, I have elected to run each simulated register as a row of REGS (a 16 by 32-bit Boolean), program length checks throughout and simulate the System/370 condition code, too.

Many of the dependent functions rely on the existence of REGS and update CC, the condition code. Wherever possible, I’ve programmed checks for System/370 abends. My old friend, the fixed point divide exception, is in there for starters.

You’ll notice that a TRACE function is called all over the place. A glance at TRACE’s code shows it to be a pretty ugly looking customer. However, when Boolean TR is on, it produces very pretty hexadecimal displays of the simulated registers. These proved very useful for debugging both the functions and the Assembler code, besides enhancing the entertainment value of the simulation.

You’ll also notice that a CHECK function is called everywhere. When Boolean CK is on, it checks that function arguments are correctly-formed. If not, it notifies an error. This error might be considered the equivalent of an Assembly error, but I wouldn’t like to strain the metaphor too far.

Before anybody asks: no, this code is not going to do the mile in under four minutes. I take the view that, when I’m having fun, I want it to last as long as possible.

     ∇ R←A ADDL B
[1]   ⍝ Logical addition of Booleans A and B.
[2]   ⍝
[3]    R←(1+⍴A)BINARY(2⊥A)+2⊥B ⍝      Extra high-order bit
[4]    CC←(2×R[⎕IO])⌽4↑(∧/~1↓R)⌽ 0 1 ⍝ detects overflow.
[5]    R←1↓R

     ∇ R←ADDR DEC
[1]   ⍝  Convert DEC decimal address to 24-bit Boolean.
[2]    R←(24⍴2)⊤DEC

[4]    ⎕←(⍕DEC),' exceeds 24-bit address capacity.'
